Gopay System Map

How an order becomes money moving: who is allowed to call the API, the request path from OrderController down through payment routing and card vaulting, the simulated bank that answers later, and the state machine that keeps every payment's status honest. This page is updated in place as new pieces of gopay get built.

Domain model

Two records, two lifecycles

An Order is what a merchant wants paid — an amount, a receipt, a currency. A Payment is one attempt to pay it. One order can carry many payment attempts (retries, different methods); gopay keeps the two as separate entities on purpose so a failed card attempt doesn't erase the order underneath it.

EntityStatus enumValues
OrderRecord OrderStatus CREATED → ATTEMPTED → PAID / CANCELLED
Payment PaymentStatus CREATED, AUTHORIZING, AUTHORIZED, CAPTURING, CAPTURED, SETTLED, PARTIALLY_REFUNDED, REFUNDED, FAILED, CANCELLED, AUTH_EXPIRED

Every entity extends BaseEntity, which now carries createdAt/updatedAt and createdBy/updatedBy. Spring Data auditing fills all four on save; the "who" comes from SecurityAuditorAware, which reads whoever the request's filter put in SecurityContextHolder — a merchant's email on the JWT chain, an API key's keyId on the API key chain, or SYSTEM with no caller at all (signup, the bank callback simulator).

§1

Order lifecycle

Orders move in one direction. POST /v1/orders creates one in CREATED. The first payment attempt against it flips it to ATTEMPTED regardless of outcome — gopay cares that an attempt was made, not whether it succeeded. Only a CAPTURED payment moves the order to PAID; cancelling is only legal before that point.

§2

Payment flow: routing by method

PaymentServiceImpl.initiate() doesn't know how to charge a card, a UPI handle, or a bank account — it only knows how to ask the right thing to try. It hands off to a PaymentGatewayRouter, which picks the PaymentAdapter for the order's PaymentMethod. Every adapter funnels into a second router, PaymentProcessorRouter, which picks the mock network simulator. Card is the one method with a real detour: it has no raw card number to send, only a vault token, so the adapter hands off to VaultService first to resolve and decrypt it.

What each processor actually returns

None of the four processors call a real bank. Each one simulates an outcome and hands back a PaymentProcessorResponse — Pending, Success, or Failure — which the adapter translates into the gateway-facing PaymentResult that PaymentServiceImpl actually acts on. At initiate time only Pending or Failure ever comes back. Success exists on the types, but no processor returns it: the final answer arrives later through the bank callback (§3).

§3

Bank callback & auto-capture

initiate() never ends in success. A processor that accepts the request answers Pending, the payment moves to AUTHORIZING, and nothing else happens until "the bank" calls back. There is no real bank, so BankCallbackSimulator plays that part: a scheduled job that wakes up, finds the payments still waiting, and answers the ones whose time has come.

What one poll does

  • Runs every polling-interval-ms (5 s, as a fixedDelay).
  • Loads AUTHORIZING payments last updated inside the lookback window.
  • Works out when each one is due: updatedAt + delay, where delay = minDelay + abs(paymentId.hashCode()) % (maxDelay − minDelay). SLOW mode doubles it. A payment that is not due yet is skipped.
  • For a due payment, compares abs(paymentId.hashCode()) % 101 with the method's success rate. The same payment id always gets the same delay and the same outcome.
  • Calls PaymentService.resolveAuthorization(...) with approve or decline.

What resolveAuthorization does

OutcomeEvents appliedResult
approve AUTHORIZE_SUCCESS → CAPTURE_REQUEST → CAPTURE_SUCCESS Payment CAPTURED, order PAID. authorizedAt, capturedAt and bankReference (METHOD_<random>) are set.
decline AUTHORIZE_FAIL Payment FAILED with error code <METHOD>_DECLINED.
stale none The payment is no longer AUTHORIZING, so the call is logged as a warning and ignored.

Per-method delay and success rate live under payment.simulator.method in application.yaml; chaos-mode overrides the dice for the whole simulator.

The lookback window has to be longer than the longest possible delay, or a payment ages out of the query before it is due and stays AUTHORIZING forever. It is computed from the config: the largest max-delay-ms (doubled in SLOW mode) plus one polling interval.

§4

Card vault & encryption

A tokenized card is stored as envelope encryption, not a single layer: each card gets its own randomly generated AES key (the DEK), which encrypts the PAN. The DEK itself is then encrypted by one shared master key before either ever touches the database. Losing the database alone gets an attacker nothing; they'd also need the master key to unwrap even one DEK.

CVV is accepted on TokenizeCardRequest but never stored anywhere — not on VaultCard, not on CardToken. PCI-DSS forbids retaining it past authorization.

§5

Payment state machine

Every status change on a Payment goes through PaymentStateMachine.transition(payment, event) — a lookup table keyed on (currentStatus, event), never a bare setStatus(). An event that isn't legal from the current status throws instead of silently moving the payment somewhere it shouldn't be. PaymentTransitionService wraps this with an audit row on every change: who triggered it, what event fired, what status it left and entered.

Capture is automatic. When the bank callback approves, resolveAuthorization applies AUTHORIZE_SUCCESS, CAPTURE_REQUEST and CAPTURE_SUCCESS back to back in one call. AUTHORIZED is real and shows up in the audit log, but a payment never rests there. The manual PUT /v1/payments/{id}/capture endpoint only works from AUTHORIZED, so while auto-capture is on it has nothing to act on.

§6

Authentication: two chains, one merchant

gopay has two kinds of caller, and each gets its own Spring Security filter chain. Someone using the dashboard logs in and carries a JWT. A merchant's server calling the payment API carries an API key and secret. Each chain claims its own URL prefixes with securityMatcher, so a request is handled by exactly one of them. Whichever filter accepts the credentials writes the merchant id into a request-scoped MerchantContext, and controllers read it from there. No controller takes a merchant id from the URL or the body.

ChainCredentialWhen it fails
JWT
signup and login are public		 Authorization: Bearer <jwt> No token, or a bad or expired one: 401. A valid token whose user was deleted: 401 INVALID_TOKEN.
API key Authorization: Basic base64(keyId:keySecret) No header: 401. Not valid Base64, or no keyId:keySecret shape: 400 MALFORMED_API_KEY_CREDENTIALS. Unknown key, revoked key or wrong secret: 401 INVALID_API_KEY.

Logging in

POST /v1/auth/login hands the email and password to the AuthenticationManager, which loads the AppUser through MerchantUserDetailsService and checks the BCrypt hash. On success, JwtUtil signs an HS256 access token with the email as subject and the merchant id and role as claims. Passwords are hashed with BCrypt at signup. An unknown email and a wrong password return the same error.

Access token + refresh token

A JWT can't be revoked early — it's trusted on signature and expiry alone, nothing is looked up. gopay's answer is the standard one: keep the JWT short-lived, and pair it with a second, server-tracked token that can actually be killed. Login returns both.

TokenFormLifetimeRevocable?
accessToken JWT (sub, merchantId, role), signed HS256 15 min — jwt.expiration-ms no — expires on its own
refreshToken "<tokenId>:<secret>" — opaque, not a JWT 7 days — jwt.refresh-expiration-ms yes — a row in refresh_token

The refresh token is built the same way an API key is: tokenId is the public lookup half, stored in plain text; secret is only ever stored as a BCrypt hash. POST /v1/auth/refresh checks both, then rotates — it revokes the token just used and returns a brand new accessToken and refreshToken together. The old one stops working immediately, even if it hadn't expired.

What /v1/auth/refresh seesResponse
Valid, unused, unexpired 200 new access + refresh token pair; old one revoked
Already revoked (rotated or logged out before) 401 INVALID_REFRESH_TOKEN — treated as theft: every refresh token for that app user is revoked, not just this one
Expired, or malformed (no :), or secret doesn't match 401 INVALID_REFRESH_TOKEN — same error for all three, so a caller can't tell which

Rotation and reuse-detection aren't a JWT property — they come from checking a server-side record on every use, which is exactly what makes a refresh token revocable and a plain access-token JWT not. A stolen refresh token still works for whoever holds it until it's rotated or the real owner's next refresh collides with it; the short access-token lifetime is what bounds the much more common leak (a token that rides on every request), and POST /v1/auth/logout (always 204, even for an unknown or already-revoked token) is how a merchant kills a session on purpose.

API keys

  • A key has a public keyId (gopay_TEST_… or gopay_PROD_…) and a secret. The secret is returned once, when the key is created or rotated.
  • Only a BCrypt hash of the secret is stored. Revoking a key disables it.
  • Rotating issues a new secret. The previous one keeps working for one day (the grace period) so a merchant can switch over without downtime.
  • Keys are managed from the JWT side, at /v1/merchants/api-keys, for the logged-in merchant only.

/v1/admin/** and /actuator/** are reserved for the admin side. Today they only require a valid login; a role check for ADMIN is not enforced yet.

§7

Redis: one instance, three separate jobs

gopay points three unrelated pieces of request-handling machinery at the same Redis instance, each with its own key prefix so they never collide, and each with its own answer to the one question that actually matters for a shared cache: what should happen if Redis itself fails right now? The right answer is different every time.

JobKey prefixWhat a hit/miss meansOn a Redis failure
Cache
skip a DB lookup		 apikey: hit → skip the database; miss → load it and cache it for next time fails open — falls back to the database, same as a miss
Rate limit
cap request volume		 ratelimit: a counter (or sorted set, or token bucket) tracking how much of a quota is left fails open — allows the request rather than blocking real traffic during an outage
Idempotency
block duplicate side effects		 idempotency: a claim (then a replayable result) for one specific client-supplied key fails closed — the claim throws instead of guessing; see why below

The failure-mode column is the one thing that is not interchangeable between these three. A cache or a rate limiter can safely fail open, because something else (the database, or simply allowing the request) is still correct on its own. Idempotency can't: the entire reason it exists is to stop a payment from being processed twice, so a wrong guess during an outage — in either direction — causes real harm. That is why IdempotencyStore.setIfAbsent is the one Redis call in gopay that is allowed to throw a real exception back to the caller instead of quietly recovering.

API key cache (Redis)

Every API-key request used to mean a database lookup plus a BCrypt check against the stored hash, every single time. ApiKeyAuthenticationFilter now checks Redis first: loadAndCache(keyId) returns a cached ApiKeyCacheEntry snapshot (merchant id, both secret hashes, grace period, enabled) when one exists, and only falls back to ApiKeyRepository on a miss — caching the result it finds for next time. The cache only ever accelerates the success path; a wrong secret always falls through to the database, since the cache alone cannot tell a wrong secret apart from one that is only valid because of the grace period.

EventCache effect
First request for a keymiss → DB load → cached, TTL 5 min ± 60 s jitter
Next request, same keyhit → no DB round trip, no fresh BCrypt-against-DB-row work
revoke / rotateevicted immediately — does not wait on the TTL to catch up
Redis unreachablefails open to the DB — a cache outage never blocks real authentication

The TTL is 5 minutes plus or minus 60 seconds of jitter, not a flat 5 minutes, to avoid a cache stampede: a burst of keys cached around the same moment would otherwise all expire in the same instant and all miss Redis together, right back to hammering the database at once.

Rate limiting

ApiKeyAuthenticationFilter checks a RateLimiter before any DB or cache lookup runs at all, keyed per keyId — a brute-force run against one key cannot drown out another key's quota, and a wrong secret never even reaches loadAndCache once a key is being hammered. The active implementation, FixedWindowRateLimiter, is one Redis INCR per window: 100 requests per minute, per key (ApiKeyRateLimitPolicy).

OutcomeResponse
Under the limit normal response, plus X-RateLimit-Limit and X-RateLimit-Remaining headers on every call — allowed or denied — so a cooperative client can see its quota and self-throttle before ever being rejected
Over the limit 429 RATE_LIMIT_EXCEEDED with a real Retry-After header

Two more algorithms live in common/ratelimiting/impl for comparison, neither wired up — only FixedWindowRateLimiter is a @Component:

  • SlidingWindowRateLimiter — a true rolling window (a Redis sorted set scored by request time), so no boundary burst the way fixed windows have, at the cost of more Redis work per check.
  • TokenBucketRateLimiter — lets a caller burst up to the full limit at once after being idle, then throttles back to the steady average rate, instead of a hard reset per discrete window.

Each has a *Plain sibling, left deliberately broken as a teaching comparison: SlidingWindowRateLimiterPlain does prune + add + count as four separate Redis calls, which creates a boundary-only overcount under real concurrency. TokenBucketRateLimiterPlain is worse — a genuine lost update on its read-modify-write cycle, where two concurrent requests can both read the same token count and both get allowed on the one token that was actually available. The active (non-Plain) versions run the whole sequence as one Lua script instead; Redis guarantees nothing else executes while a script is in flight, which is what closes both races.

Idempotency (Redis)

A client sends X-Idempotency-Key: <their own value> on POST/PUT/PATCH — GET is already safe to repeat and DELETE is naturally idempotent on its own, so neither is guarded. This runs in IdempotencyFilter, added after the JWT/API-key filter in each chain so MerchantContext is already populated — the Redis key is idempotency:<merchantId>:<their key>, so two different merchants can safely reuse the exact same literal key without colliding.

What happensRedis call
Request arrives setIfAbsent(key, 30s) — claims the key with a fixed "IN_PROGRESS" marker, atomically; only one concurrent request can ever win this
Claim won → controller runs the real controller executes, writing its response into a ContentCachingResponseWrapper instead of the real response, so the filter can read the body back afterward — a plain HttpServletResponse has no method to do that at all, it only ever streams bytes outward
  ↳ response was < 400 store(key, body, 24h) — overwrites "IN_PROGRESS" with the real response, replayable for a full day
  ↳ response was ≥ 400, or an exception was thrown delete(key) — this attempt never actually succeeded, release it so a real retry gets through
Claim lost (duplicate) → already has a stored result replay that exact body, status 200 — no controller call, no DB hit at all
Claim lost (duplicate) → still "IN_PROGRESS" 409 DUPLICATE_IDEMPOTENCY_KEY — the first attempt hasn't finished yet

Two different TTLs, answering two different questions — and only one of them needs to be long. The claim only asks "is someone already working on this exact request, right now?" — a question that only matters for as long as one HTTP request actually takes, so 30 s is already a generous margin. Making the claim's TTL long would actively cause harm, not just waste time: it is set before the real work runs, so if the server crashes mid-request — before store() or delete() ever gets to run — the key is left stuck at IN_PROGRESS with nothing left to clean it up. A long claim TTL would mean a client retrying with the same key gets 409 for the full TTL, even though the original attempt is dead. Keeping it short lets the system self-heal: the lock just expires on its own soon after a crash, and the next retry gets through cleanly. The result TTL answers a different question — "what actually happened, so I can show it again later?" — and that has to survive a genuinely slow client retry (a mobile app regaining connectivity, a timeout), which is why it gets real hours (24 h, the same convention Stripe uses) instead of seconds.

IdempotencyStore.setIfAbsent is the one place in the whole codebase that deliberately does not fail open on a Redis error, unlike the API key cache or the rate limiter. Guessing wrong here is unsafe in either direction: treating a Redis failure as "key was absent" could let a payment be processed twice during an outage; treating it as "already claimed" would block every first attempt. So it throws, and a client retrying with the same key is the correct recovery once Redis is back. store/get/delete all run only after that decision is already safely made, so each of them logs and continues on failure instead of propagating — a failed write-back or cleanup must never turn an already-successful payment into an error response.

§8

Demo scenarios

The mock processors roll a weighted die for most charges (roughly 70% pending, 30% declined) so the system feels alive — but a demo shouldn't run on luck. These inputs are wired to deterministic outcomes, the same convention real gateways use for sandbox test cards.

Any chaos-mode: ALWAYS_FAIL BankCallbackSimulator <METHOD>_DECLINED
Any anything else ThreadLocalRandom ~70% PENDING  /  ~30% FAILED

A payment that comes back PENDING is not finished. The callback simulator settles it a few seconds later: approved payments capture on their own, and the order turns PAID. The outcome is fixed per payment id, so the same payment always ends the same way.

Walking through it

  1. POST /v1/auth/signup, then POST /v1/auth/login to get a token.
  2. POST /v1/merchants/api-keys with the token. Copy the keyId and keySecret; the secret is shown once.
  3. With Basic auth (keyId as username, keySecret as password): POST /v1/orders, then POST /v1/payments with that order id.
  4. Wait 5 to 15 seconds, then GET /v1/orders/{id}/payments to see the settled status.
